### 당근 Tech

#### 파드는 떴는데 왜 통신이 안 될까? kube-proxy nftables 전환 여정
원문: https://medium.com/daangn/%ED%8C%8C%EB%93%9C%EB%8A%94-%EB%96%B4%EB%8A%94%EB%8D%B0-%EC%99%9C-%ED%86%B5%EC%8B%A0%EC%9D%B4-%EC%95%88-%EB%90%A0%EA%B9%8C-kube-proxy-nftables-%EC%A0%84%ED%99%98-%EC%97%AC%EC%A0%95-545dfd2cfc4f?source=rss----4505f82a2dbd---4

- 당근 SRE팀 클러스터 파트는 쿠버네티스 환경의 서비스 안정성을 개선하기 위해 kube-proxy를 iptables 모드에서 nftables 모드로 전환하기로 했다.
- 새 노드에서 kube-proxy가 네트워크 규칙을 준비하기 전에 Pod의 애플리케이션이 먼저 시작되면 DNS 조회나 다른 서비스와의 통신에 실패할 수 있다.
- 올해 상반기 Karpenter를 도입하며 여유 노드를 미리 띄우던 Overprovisioner를 제거하자, 새 노드에 Pod가 즉시 배치되면서 규칙 동기화 전 통신 실패 제보가 늘었다.
- 2026년 상반기 클러스터 규모가 약 1,400개 Service, 27,000개 Pod, 80,000개 NAT 규칙으로 커지면서, 노드 생성 시 초기 전체 규칙 동기화에 최대 4분 20초가 소요됐다.
- Service와 Endpoint를 순차 비교해 조회 비용이 O(N)인 iptables 모드와 달리, nftables 모드는 목적지 IP·프로토콜·포트를 키로 하는 map 기반 조회로 처리한다.

#### 실행 중인 파드에 왜 연결할 수 없을까? kube-proxy nftables 모드 전환 여정
원문: https://medium.com/daangn/why-cant-my-running-pods-be-reached-our-journey-to-kube-proxy-nftables-mode-6fceb1d2a5f7?source=rss----4505f82a2dbd---4

- 당근(Karrot) SRE팀 클러스터 스쿼드는 모든 서비스가 동작하는 쿠버네티스 플랫폼에서 kube-proxy를 iptables 모드에서 nftables 모드로 마이그레이션한 과정을 공유했다.
- 모든 노드에 배포되는 kube-proxy가 커널 네트워크 규칙을 설정하기 전에 새 노드의 애플리케이션이 먼저 시작되면 DNS 조회나 다른 서비스 호출이 실패할 수 있다.
- 2024년부터 한국 프로덕션 클러스터에서 kube-proxy 규칙 동기화 지연이 관측됐으나 실제 장애로 이어지지는 않았다.
- 올해 상반기 Karpenter를 도입해 빠른 노드 확장이 가능해지면서 Overprovisioner 사용을 중단했고, 그 결과 새 노드에 Pod가 바로 배치되며 통신 불가 제보가 증가했다.
- 2024년과 2026년의 kube-proxy 지표를 비교한 결과, 2년 사이 서비스 규모와 NAT 규칙 수가 증가하면서 kube-proxy의 작업 부하가 뚜렷하게 커진 것으로 나타났다.

#### 직렬화와 압축 기술 선택으로 Redis 비용 낮추기
원문: https://techblog.woowahan.com/28276/

- 백엔드 대량 트래픽 환경에서 Redis 캐시 값이 커지면 메모리 비용과 eviction으로 인한 적중률 하락, 네트워크 대역폭 한계, 단일 스레드 명령 처리 지연, 애플리케이션의 직렬화 CPU·메모리 부담이 함께 증가한다.
- JSON은 객체마다 필드 이름을 반복 저장하고 숫자도 문자로 표현해 크기가 크며, 새로운 저장 형식을 선택할 때는 크기와 속도 외에 클래스 필드나 패키지 변경 시에도 기존 값을 읽을 수 있는 안정성까지 함께 검토했다.
- 캐시 값의 크기를 줄이는 방법으로 직렬화 형식을 바꾸는 방식과 바이트를 압축하는 방식 두 가지를 살펴봤다.
- Apache Fory는 Ant Group의 Fury에서 시작해 Apache 재단에 기증된 뒤 2025년 이름을 바꾸고 Apache 최상위 프로젝트가 된 바이너리 직렬화 프레임워크로, Java 외에도 Python, C++, Go, JavaScript, Rust 등을 지원한다.
- Fory는 필드 이름과 타입 정보를 반복 저장하지 않고 가변 길이 바이너리·맞춤 인코딩을 사용하며 런타임에 클래스 전용 직렬화 코드를 생성해 리플렉션 없이 동작하므로 반복 구조가 큰 객체에서 유리하지만, 문자열 위주 데이터에서는 차이가 크지 않다.

### 小红书技术REDtech (Xiaohongshu REDtech)

#### 샤오홍슈 스토리지 기반 분석 08｜RedKV Proxy 성능 최적화 실전
원문: https://mp.weixin.qq.com/s?__biz=Mzg4OTc2MzczNg==&mid=2247497216&idx=1&sn=8f63447eb5378a400503a6d25cfce6a0

- 샤오홍슈의 RedKV Proxy V3 경로는 워커 스레드 이벤트 루프를 공유하는 InternalSDK를 통해 KVServer에 접근하며, 소형 GET은 객체 생성·파싱·상태 등록, 대형 GET/SET은 메모리 복사와 송수신 배치, 대형 MGET은 이벤트 루프 점유가 주요 병목으로 작용한다.
- 소형 요청에서는 프런트엔드의 파싱 결과와 최초 라우팅 결과를 재사용하고 워커 스레드 내 요청 객체 풀을 활용했으며, 완료 콜백을 별도 해시 테이블 대신 요청 큐에 통합해 소형 GET 단독 대조군에서 처리량을 약 0.60%~1.47% 높였다.

- 유한 배칭에서는 이벤트 루프 끝에서 요청·응답을 일괄 전송하되 80B 이하 짧은 프레임은 최대 5KiB 임시 스택에 복사해 단일 세그먼트로 묶어 보내고, 대형 GET 수신 버퍼를 조건부로 한 단계 확장해 64KiB GET의 수신 호출을 요청당 약 1.06~1.10회에서 0.57~0.62회로 낮췄다.
