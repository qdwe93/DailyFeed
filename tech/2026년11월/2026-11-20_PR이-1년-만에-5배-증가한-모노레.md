### 자체 개발 Background Agent 'haro'를 'haro' 내부에서 개발하며 터미널 버리기
원문: https://tech.layerx.co.jp/entry/haro-in-haro

- haro는 LayerX 바쿠라쿠 사업부가 자체 개발한 Background Coding Agent로, Web UI나 Slack에서 호출하면 클라우드 상에 개발에 필요한 도구가 갖춰진 작업 환경이 생성된다.
- haro의 실행 환경은 EKS 위에서 Workspace 및 WorkspaceProfile 커스텀 리소스(CRD)와 커스텀 컨트롤러를 통해 workspace Pod와 브라우저 확인용 프리뷰 URL의 라이프사이클을 관리한다.
- 컨트롤러 등 haro의 환경 측 기능을 haro 내부에서 개발하려면 Workspace를 생성해 Pod가 Running 상태가 되는지 확인할 전용 Kubernetes 클러스터가 필요했다.
- 초기에는 EKS 호환 클러스터 도구인 fjord를 이용해 workspace Pod 안에 클러스터를 직접 띄웠으나, 외부 클러스터의 KUBERNETES_* 환경 변수 간섭과 노드 IAM 역할 부재로 인한 ECR 이미지 pull 인증 문제 등 구조적 한계로 이를 포기했다.
- 이후 workspace 내부에 클러스터를 두는 방식을 버리고, haro가 동작하는 실제 클러스터의 Namespace 안에 컨트롤 플레인만 띄우는 vCluster와 Envoy, Telepresence를 조합한 구성으로 전환했다.

### CocoaPods에서 SPM으로 — 광고 SDK 의존성 정리와 Dependabot에 의존하지 않는 업데이트 운영
원문: https://techblog.zozo.com/entry/20261120-wear-ios-cocoapods-to-spm

- CocoaPods가 2024년 유지보수 모드에 들어가고 Specs 저장소가 2026년 12월 읽기 전용으로 전환될 예정임에 따라, WEAR iOS 팀은 Podfile에 선언된 25개 외부 라이브러리를 Swift Package Manager(SPM)로 이전하는 작업을 진행했다.
- Objective-C와 Swift가 혼재된 대규모 앱에서 회귀 테스트 범위 확대와 장애 원인 분리의 어려움을 줄이기 위해 주요 라이브러리 이전은 2025년 11월부터 2026년 3월까지 약 4개월간 기능 개발과 병행하여 단계적으로 수행했다.
- Xcode GUI 추가 시 발생하는 project.pbxproj의 대규모 변경을 피하기 위해 로컬 패키지 Dependencies/Package.swift에 의존성을 모으고, 앱 본체·알림 서비스 확장·테스트 등 타깃별로 필요한 5개 product를 분리해 연결했다.
- 라이브러리는 import 파일 수가 적은 순서대로 4단계로 나누어 1 라이브러리 1 PR 방식으로 이전했으며, CI 전용 도구는 Homebrew로, 버전 통일이 필요한 SwiftFormat은 SPM 선언 후 빌드 단계 소스 빌드로 전환했다.
- 삭제 예정인 Swifter를 제외한 24개 중 20개는 SPM 이전, 2개는 SPM 대응 라이브러리 교체(LUKeychainAccess는 래퍼와 호환성 테스트를 거쳐 KeychainAccess로 교체), 2개는 Homebrew 이전을 완료했고, 광고 SDK는 비권장 어댑터의 버전 고정 문제로 2026년 10월까지 보류한 뒤 Google 공식 어댑터로 교체해 이전했다.

### Gemini API의 Tool Retrieval 기능 소개
원문: https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-tool-retrieval/

- Gemini API는 Interactions API에서 프리뷰 형태로 Tool Retrieval 기능을 출시했다.
- 수십에서 수백 개의 도구 전체 파라미터 스키마를 매 요청마다 전송할 때 발생하는 입력 토큰 증가, 지연 시간 상승, 선택 정확도 저하를 피하기 위해 전체 도구 라이브러리를 대기 상태로 두고 현재 작업에 필요할 때만 스키마를 불러온다.
- 요청에 tool_search 도구를 추가하고 보류할 도구에 defer_loading: true를 설정하면 모델은 도구의 이름과 설명만 확인하고 파라미터 스키마는 컨텍스트에서 제외한다.
- 모델이 필요한 도구를 이름으로 요청하면 API가 전체 스키마를 불러오고, 모델이 같은 단일 API 요청 내에서 함수 호출을 생성한다.
- 검색 호출(tool_search_call), 검색 결과(tool_search_result), 함수 호출(function_call)의 세 단계가 모두 interaction.steps에 기록되어 도구 이름이나 설명을 디버깅할 때 모델이 고려한 도구를 확인할 수 있다.

### 양자역학의 핵심 특성을 대규모로 검증한 연구
원문: https://blog.google/innovation-and-ai/models-and-research/quantum-computing/putting-one-of-quantum-mechanics-deepest-features-to-test-at-scale/

- 구글 퀀텀 AI는 사이언스(Science) 표지 논문으로 발표된 연구에서 자사 양자 프로세서에서 맥락성(contextuality)이 대규모로 유지됨을 입증했다.
- 맥락성은 시스템의 속성이 미리 고정되어 있지 않으며 함께 수행하는 다른 양립 가능한 측정에 따라 측정 대상이 달라지는 양자 특성이다.
- 최근까지 이러한 효과는 주로 몇 개의 입자로만 구성된 소규모 시스템에서만 확인되었다.
- 연구진이 양자 프로세서를 사용한 결과 큐비트가 협동 게임에서 98.3%의 승률로 고전적 한계인 88.9%를 넘었으며, 최대 105큐비트 규모의 작업에서 제약된 고전 전략을 능가했다.
- 이 테스트는 미세한 하드웨어 오류를 포착하는 민감한 새로운 방법으로도 활용되어 화학 및 재료과학 같은 실세계 응용 분야로 나아가는 데 도움을 준다.

### 다른 AI 앱의 대화 기록을 제미나이로 이전하는 방법
원문: https://blog.google/innovation-and-ai/products/gemini-app/switch-ai-assistants-transfer-history/

- 사용자는 다른 AI 어시스턴트에서 사용하던 맥락, 선호도, 대화 기록을 제미나이(Gemini)로 가져와 처음부터 다시 시작하지 않고 이용할 수 있다.
- 선호도를 옮기려면 제미나이 가져오기 설정을 열어 제공된 프롬프트를 복사한 뒤 기존 AI 도구에 붙여넣어 선호도 요약을 생성해야 한다.
- 기존 AI 도구에서 생성된 선호도 요약 응답은 제미나이에 붙여넣어 적용한다.
- 대화 기록을 이전하려면 기존 AI 서비스 제공업체의 계정 설정에서 대화 기록을 ZIP 파일로 내보내야 한다.
- 내보낸 ZIP 압축 파일을 제미나이 설정에 업로드하면 중단했던 지점부터 대화를 이어갈 수 있다.

### 오픈AI의 퍼포먼스 팩토리가 ChatGPT 속도를 유지하는 방법
원문: https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast

- 오픈AI는 클라우드에서 실행되며 코덱스(Codex)와 자사 모델을 활용해 성능 저하를 자율적으로 조사하고 해결하는 '퍼포먼스 팩토리(Performance Factory)' 시스템을 구축했다.
- 엔지니어가 반복 작업의 워크플로와 지침을 정의하면, 회귀 워크플로(Regression Workflow)는 성능 경보 발생 시 작업을 열어 에이전트가 속도 저하 조사, 결과 기록, 엔지니어 검토용 수정안 제안을 수행하도록 한다.
- 수정 사항이 배포된 후에는 다른 에이전트가 동일한 작업을 이어받아 성능이 기준선(baseline)으로 복구되었는지 확인한다.
- 회귀 워크플로는 3개월이 조금 넘는 기간 동안 매일 17건꼴로 총 1,700건 이상의 조사를 추적했으며 600건 이상에서 근본 원인을 규명했다.
- 코덱스 도입 전에는 엔지니어들이 CPU·할당 프로파일러 등 30개 이상의 성능 도구를 구축해 지표를 수동으로 분석했으나, 코덱스를 파트너로 도입한 후에는 익숙하지 않은 시스템에서도 대규모 코드베이스를 검색하고 관련 지표와 트레이스를 찾을 수 있게 되었다.
